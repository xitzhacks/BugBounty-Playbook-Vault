# HUNT tRPC ON NEXT.JS (procedure names hidden by Proxy)

## 1. Detect tRPC
- Network tab / bundle greps show `@trpc/client`, `@trpc/react-query`, `@trpc/server`, `createTRPCReact`, `httpBatchLink`, `/api/trpc`.
- Endpoint shape: `GET/POST https://host/api/trpc/<proc>[?batch=1][&input=...]`
- tRPC v10+ with `httpBatchLink` sends `?batch=1` and batches multiple calls; single calls still work without batch.

## 2. The status-code oracle (blind procedure discovery)
Because procedure names are generated by a JS Proxy at runtime, they do NOT appear as literal strings in the minified bundle. Enumerate by probing candidate names and reading the HTTP status:
- `404` + body `{"error":{"json":{"code":"NOT_FOUND",...}}}` => bogus procedure (real 404).
- `401` `UNAUTHORIZED` => REAL procedure, auth-gated.
- `405` => REAL procedure that is a mutation (needs POST); GET not allowed.
- `200` => REAL public procedure.
- `400` with zodError => REAL procedure, wrong/empty input shape.

Probe format:
```
curl -s -o /dev/null -w "%{http_code}" "https://host/api/trpc/<proc>"
# mutation:
curl -s -X POST "https://host/api/trpc/<proc>?batch=1" \
  -H "Content-Type: application/json" \
  -d '{"0":{"email":"x@y.z","password":"Passw0rd!"}}'
```

## 3. CRITICAL PITFALL — Cloudflare / WAF rate-limit
- Hammering thousands of candidate procedure names (e.g. 6885 requests in ~100s) trips Cloudflare's bot management. After that, EVERY request returns `403` regardless of validity. The 403 list is then GARBAGE — do NOT trust it as a procedure map. (This happened in a live oripaone.jp session: the second sweep returned 6885 requests all 403; only the first ~40-request precise run was trustworthy.)
- Mitigations:
  - Run a SMALL precise wordlist first (domains x verbs, ~40-80 names). Trust THAT result.
  - Space requests (sleep 1-3s) or use low concurrency (5-10 threads), NOT 25.
  - Prefer driving the real browser (it holds a valid CF clearance cookie) over curl for live testing after enumeration.
- **Egress-IP bypass when YOUR IP is throttled:** `web_extract` (and Browserbase) egress from a DIFFERENT IP than your shell. When `curl` from the terminal returns `403` on a known-good endpoint but `web_extract` of the same URL returns `200`, the throttle is per-IP. Use `web_extract` to keep probing/confirming while your shell IP cools down. This is NOT a substitute for authenticated testing (web_extract can't send POST bodies or cookies), but it keeps recon + unauth confirmation alive during a cooldown.
- If you already got rate-limited: STOP curl, wait 10-30 min for the IP cooldown, and verify with a single known-good request (e.g. a public proc that returned 200 earlier) before trusting any 403/404.

## 3b. Recovering REAL procedure names the Proxy hides
The bundle only shows LITERAL call sites, not the generated path. Extract them:
- grep the bundle for `.useQuery`/`.useMutation`/`.useInfiniteQuery` chains: `trpc.<group>.<proc>.useQuery(...)` reveals real names like `user.me`, `notifications.unreads`, `pack.bySlug`, `maintenance.status`, `user.loginState`.
- Also catch inferred nodes from tRPC error responses: `"path":"<proc>"` in 401/400 bodies names the real procedure even when your call was wrong (e.g. `"path":"pack.bySlug"` on a 400 zodError).
- Build your unauth/401/405 map from these recovered names PLUS the status-code oracle (§2), not from blind fuzzing alone.

## 3c. PITFALL — input-shape ambiguity on 400 "必須"
When a procedure returns `400` with `zodError.formErrors:["必須"]` (required) at root `path:[]` for EVERY field name you try (`slug`, `id`, `packId`, `packSlug`, ...), the issue is usually NOT the field name — it's the input ENCODING. tRPC over `httpBatchLink` wraps input as `{"0":{...}}`; single (non-batch) calls may expect the raw object. Don't brute-force param names endlessly (rate-limit trap, §3) — resolve the exact call shape from the browser network tab (see §7: drive the real browser, watch the XHR `input` JSON). The `pack.bySlug` case at oripaone.jp rejected all variants anon and needed the browser to learn the real shape.

## 5. IDOR testing (object-style procedures)
Once you have 2 test accounts (register both; program rules may require email to contain a keyword — e.g. "issuehunt"):
- `address.update` (405 POST): object takes an id/userId. Swap it to the OTHER account's address id → does it write? That's IDOR/write.
- `payment.history` / `payment.detail` (401, needs auth): call with account A's session but pass account B's id/orderId in the input → does it return B's data? IDOR/read.
- `notifications.byId` (401): same swap.
- `product.byId` returning 401 is suspicious — a public catalog should be unauthenticated. Investigate (maybe leaks more authed, or is a misconfig).

## 6. Mass assignment
On `user.create` / `user.updateProfile` / `auth.signUp`, send extra privileged fields the UI never sends:
`{"is_admin":true,"role":"admin","verified":true,"email_verified":true,"permissions":["admin"],"tenant_id":1}`
If the server blindly applies DTO fields, low-priv account becomes admin (chain with hunt-ato / hunt-auth-bypass).

## 7. Auth / password reset
- `auth.resetPassword` / `auth.sendResetPassword`: test token reuse, missing expiry, and whether a logged-in session can change email/password WITHOUT re-authentication (account takeover primitive).
- `user.create` may wrap `supabase.auth.signUp` — the session is then stored in a cookie (secure, samesite=lax) that tRPC reads. Capture it via the browser, not curl, for authenticated calls.

## 8. Public unauthenticated reads
- Procedures like `config.get` returning 200 unauthenticated confirm the API answers unauth requests. Enumerate other public reads (they may leak internal data, feature flags, or PII).
- Supabase Storage URLs in HTML (`/storage/v1/render/image/public/...`) are EXPECTED public and not a finding.

## 9. Anti-pattern: don't waste time on static anon-key extraction
- Next.js + Supabase often ships a BUILD-TIME PLACEHOLDER anon key (e.g. `eyJhbG...iLCJ...` ~208 chars with literal `...`) in the bundle. It is NOT a valid JWT and cannot call Supabase directly.
- The real anon key + project URL are injected at runtime via Next.js runtime config / RSC and are NOT exposed to anonymous users. Skip this dead end; pivot to the tRPC layer.

## 10. Tooling notes
- Use a real browser (Browserbase / Playwright) for the authenticated phase — it holds CF clearance and the session cookie, and lets you register accounts through the actual UI (respecting program email rules).
- When the browser backend is 502/down, STOP and wait; don't burn the IP with curl.
