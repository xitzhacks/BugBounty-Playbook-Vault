# CTF — Find the Genuine Item (reverse a stamp/hash derivation)

## When to load
- A challenge supplies a batch of records (often hundreds), each with metadata fields (id, nonce, batch, operator, notes, ...) AND a **claimed computed value** — typically a `stamp: BI{<hex>}` / `signature` / `hash` field.
- The brief says something is "not quite right", "identify the genuine one", "fake vs real", "verify the process", or "examine the supplied records". Often 0 solves / low solves.
- Hints like *"derived deterministically from metadata"*, *"reproduce the stamping process and compare"*, *"pay attention to byte order, direction, field representation"*.

## Core idea
Most records are **forgeries**: their printed value is random and will NOT match any deterministic function of their metadata. Exactly **one** record is genuine: `printed_value == f(metadata)` for the *correct* function `f`. Your job is to discover `f` and surface that one record (its printed value usually IS the flag, or derives it).

## Workflow

**Step 0 — Read the hints word-for-word and map each clause to a grid axis BEFORE writing code.** This is the single most common failure mode on this challenge class: firing broad hash sweeps that ignore the hint text (the user will explicitly say *"strictly follow the hints"* / *"focus only on the hints"* when you drift). For the canonical hints — *"derived deterministically from metadata"*, *"reproduce the stamping process and compare"*, *"pay attention to byte order, direction, and field representation"* — the mapping is:
- *"metadata"* → enumerate EVERY field present (id, nonce, notes, qc, …), not just the two obvious ones.
- *"reproduce … for every unit and compare"* → the ONLY valid test is a full-population exact-1 score (never validate a candidate on one hand-picked unit).
- *"byte order, direction, field representation"* → these three words ARE your grid: `reps()` must cover each field as (ASCII string / raw hex-bytes / int-BE / int-LE / reversed-bytes / decimal-string) AND every concatenation order AND digest direction (forward / reversed / word-swapped) AND truncation window. If your `reps()` grid doesn't literally exhaust those three axes, you have not followed the hint.
Write the grid down, then let the scorer enumerate it. Do not add algorithms the hints do not imply, and do not keep re-running sweeps that time out and return 0 — that IS the loop the user is warning you about.

1. **Parse all records** into structured form (unit_id, nonce, stamp_hex, extra fields) and save to JSON for fast iteration — don't hand-inspect.
   - **Confirm parser fidelity with raw bytes first.** Before trusting the parse, `cat` a sample record and `od -b` it (octal bytes). Verify there are no hidden fields, trailing-whitespace tricks, or a separator different from what your parser assumes. CTF7 "Fake Flag Factory": the user literally asked `cat` then `od -b`, and it confirmed the file was exactly `unit_id`/`nonce`/`stamp`/`[batch|shift|operator|notes]`/`qc` with no hidden input — which ruled out a secret field early.
2. **Hypothesize the derivation space**, driven by the hints:
   - *field representation*: try each field as (a) its ASCII string, (b) raw bytes of a hex value, (c) integer big-endian (4 bytes), (d) integer little-endian (4 bytes), (e) ASCII of the hex *string* itself (8 bytes, not decoded), (f) the hex *string reversed* then decoded.
   - *byte order / direction*: concatenate field-blocks in several orders; try reversing the whole digest and/or byte-swapping 4-byte words; try reversing the nonce/uid bytes before hashing.
   - *function*: md5 / sha1 / sha256 / sha512 / blake2b, usually **truncated to the byte length of the printed value** (12 bytes = 24 hex is common).
   - *structural embedding (NOT a hash)*: the stamp may **contain or equal** metadata bytes — test `stamp[:4] == nonce_bytes`, `stamp[:4] == nonce_rev`, `stamp contains nonce_bytes`, `stamp XOR nonce_bytes == uid_bytes(any repr)`, and `int(stamp) == (nonce<<k)|uid` for small k. Genuine units reveal a clean relationship here; fakes won't.
   - *arithmetic/bitwise construction*: treat the 12-byte stamp as a 96-bit int and test `nonce_int<<32 | uid`, `uid<<32 | nonce`, `nonce ^ uid`, `nonce + uid`, `nonce * uid` (mod 2^96), packed BE/LE with raw/rev/word-swap. Some challenges build the stamp by *packing* integers rather than hashing.
   - *header/constant salt*: the challenge's constant file header (e.g. `Fake Flag Factory :: assembly line`) or the challenge name may be a salt: `md5(salt + nonce)` etc.
2b. **Run a fake-generator pre-scan (decoy diagnostic).** Score every candidate formula by **how many records it matches**, not just whether it hits exactly one. See `scripts/fakegen_scan.py`.
   - If a formula matches **>=5 (or ~all) records**, that is the **fake generator**; the genuine item is the *outlier* — the record(s) that do NOT match it (or that match a different formula). This inverts the problem: find the generator, then the outlier is the answer.
   - If **NO formula matches >=5 records** (as in CTF7 "Fake Flag Factory": best was 1), the fakes are **independent noise** — there is no shared generator to reverse, so the genuine can NOT be found by hashing metadata. Pivot immediately to: (a) a server-side secret/salt you weren't given, (b) a structural/arithmetic quirk only the genuine unit satisfies, (c) the genuine being identifiable by a validity marker (see Pitfalls), or (d) asking what the "verification process" actually is. Do not burn more cycles brute-forcing hash functions once the pre-scan shows fakes are noise.
3. **Score, don't eyeball — and NEVER validate on a single unit.** For each candidate `(field-set, hash, transform)`:
   - compute `f(rec)` for **every** record,
   - count how many printed values it reproduces.
   - The correct derivation reproduces exactly **1** record (the genuine one) — or N if the challenge expects several. A candidate matching 0 or many is wrong.
   - **Anti-loop rule (critical):** Do NOT test a candidate algorithm against one hand-picked unit (especially not one whose `notes:` says "trust me" / "definitely real" — those are decoys). A correct algorithm tested on a decoy will never match, so 0-matches proves nothing and only manufactures a loop. The only valid test is: scan the FULL population and look for the algorithm that reproduces exactly one record. If after a reasonable sweep NO algorithm matches exactly one record, the derivation is NOT a standard hash you can guess — STOP firing more hashes (see Pitfalls: looping) and pivot.
4. **Quick planted-flag / wordlist check.** Before deep reversing, grep all records for any `BI{...}` (or other flag shape) appearing *outside* the stamp field (some authors plant the real flag in a `notes:` line), and test whether any stamp equals a hash of a common word ("genuine", "real", "flag", challenge name, author). Cheap and occasionally decisive.
5. **Extract the flag** from the uniquely-matching record (the printed value is the flag, or the value derives it).

## Search script (reusable)
See `scripts/brute_stamp.py` — a generic scorer: parse `unit_NNNN.dat`-style records, brute-force field-combination × hash × transform, and print candidates that match exactly 1 record. Adapt the `reps()` function to your field names.
See also `scripts/landscape_stamp.py` — the broader version used on "Fake Flag Factory": same idea but covers single/pair/triple field combos × all 5 hashes × 4 output transforms × every 12-byte digest window, AND includes a dedicated PASS-only check. It reports ALL exact-1 candidates with their `qc` status so decoys (e.g. a lone match on a `qc: FAIL` record) are visible. Start with this one.
See `scripts/fakegen_scan.py` — the **fake-generator pre-scan**: scores every single/double-field hash formula by match COUNT and prints any matching >=5 records. Run this FIRST (before the exact-1 scorer): if nothing matches >=5, the fakes are independent noise and no metadata hash will ever yield the genuine item (see Workflow step 2b) — pivot to secret/structural/validity-marker approaches instead of brute-forcing more hashes.

## Worked example (and a trap to learn from)
CTF7 "Fake Flag Factory" (see `references/fake_flag_factory.md`): 1000 units, 696 with a `BI{<24hex>}` stamp; hints were *"derived deterministically from metadata"*, *"reproduce the stamping process and compare"*, *"byte order, direction, field representation"*.

Brute-forcing **every** hash (md5/sha1/sha256/sha512/blake2b) × byte representation (BE/LE 2/4-byte, ASCII, decimal, reversed) × single/double/triple field combo × output slice/transform × CRC variants over all 696 records, the **only** deterministic match was `md5(nonce as raw 4 bytes)[:12]` → **unit_0380** (`nonce b57be44a` → `5147dccdc34d33223dac7cb2`), which was flagged **qc: FAIL**. That unit was a **planted decoy**: it satisfied the unique-match rule, but was explicitly marked failed-QC and the platform rejected the resulting flag. The genuinely correct derivation was never recovered in that session — the durable lesson is the trap, not the value. **A unique match is necessary but NOT sufficient** (see Pitfalls).

## On rejection / recheck procedure
If the platform rejects your candidate flag, do NOT just re-confirm the prior match — re-verify from scratch (this is the explicit "check each step so nothing is left" workflow):
1. **Re-extract the archive cleanly** (fresh `unzip`) and re-parse all records to JSON; confirm the archive md5 is unchanged so you know nothing was corrupted between runs.
2. **Re-run the FULL scoring landscape**, not just the formula that produced the prior match. Report **every** candidate `(field-set, hash, transform)` that matches exactly one record, together with that record's `qc`/validity status. A lone match you already knew about is NOT confirmation.
3. **Dedicated PASS-only check:** explicitly test whether ANY `qc: PASS` (or otherwise-valid) record matches a deterministic formula. If the genuine derivation exists, it must match a valid record — a match only on a `FAIL`/invalid record is a decoy (CTF7 "Fake Flag Factory": the sole match was on a `qc: FAIL` unit, and the platform rejected it).
4. **If still only a decoy matches, enumerate alternatives before giving up:** (a) keyed/HMAC construction (one field = key, other = message; try both directions); (b) form/URL/JSON-encoded *string* templates (`nonce=b57be44a&unit_id=380`); (c) raw structural embedding where the stamp contains the nonce/uid bytes in plaintext or XORed with a constant; (d) a server-side secret/salt you were not given.
5. Only present a value as THE flag once the platform accepts it. Until then, report the strongest candidate (with its decoy caveat) and ask what the "verification process" actually is.

## Pitfalls
- **A unique match is necessary but NOT sufficient.** A planted decoy can be the *only* record satisfying an "obvious" formula (e.g. CTF7 "Fake Flag Factory": `md5(nonce)[:12]` matched exactly one unit, unit_0380 — but that unit was flagged `qc: FAIL` and the platform rejected the resulting flag). If the single match carries a contradictory validity signal, or the platform rejects it, treat it as a decoy and keep hunting or ask what the "verification process" actually is. Also sanity-check *count*: if the real generator were the formula, you'd see ~hundreds of matches, not one — a lone match is itself suspicious.
- **Do NOT loop on brute force, and do NOT scatter across unrelated walls.** If after a solid sweep (all 5 hashes × the standard field/byte-order/representation grid × the fake-generator pre-scan) **nothing matches exactly one record**, the derivation is not a standard hash you can guess blind — STOP firing more hashes and STOP re-probing already-locked services. The user explicitly flags this pattern ("stop doing everything wrong", "do not get stuck in loop"). Pivot decisively: (a) request the exact field order / the generator logic from the user, (b) test keyed/HMAC constructions with a fixed or empty key, (c) test interior (non-aligned) 12-byte digest windows, or (d) conclude a server-side secret/salt is required and say so. Looping on the same failing approach wastes the whole session.
- **Shell footgun in record text:** `notes:` fields like `recycled housing` contain an ampersand `&` that the shell parses as a background operator, causing the command to be rejected ("Foreground command uses '&' backgrounding"). When piping/inspecting record text via the terminal, write the analysis to a `.py` file and run `python3 file.py`, or quote the string — never inline it on a shell command line.
- **Cross-check against the challenge's own validity markers.** If records carry a `qc: PASS/FAIL` (or similar) field, the genuine item should be consistent with it; a lone match on a `FAIL` record is a red flag. Don't present a unique-match value as the flag until it is accepted.
- **Don't assume the whole-file hash.** The derivation is almost always over *specific metadata fields*, not the file bytes.
- **Truncation length matters.** Printed 24 hex = 12 bytes → take `digest()[:12]`, not the full 32-byte md5.
- **Try minimal field sets first** (just the always-present fields: id + nonce). Optional fields (batch/operator/shift/qc) are usually decoys unless the genuine record includes them.
- **`byte order / direction` is literal:** if `md5(nonce_bytes)` fails, try `md5(nonce_int_BE)`, `md5(nonce_int_LE)`, reversed digest, or 4-byte word-swap of the digest.
- **Ignore social-engineering red herrings:** notes like *"this one is definitely real, trust me"* are uniformly distributed across fakes.
- **Re-downloading the challenge file rarely changes anything — verify first.** If the user says "I downloaded it again" (`challenge_hIIbswM (1).zip`, `challenge (2).zip`, etc.), compute the archive md5/sha of the new file and compare to the original BEFORE re-running the whole solve. In CTF7 "Fake Flag Factory" the re-downloaded `(1).zip` was byte-identical to the original (same md5 `68c834fa...`) — the dataset was unchanged, so re-solving produced the same decoy. Confirming the checksum first avoids wasted effort and false hope that "new data" will fix a stuck solve.
- **Re-extraction always:** even when the zip is identical, re-extract fresh (`unzip -o -q`) into a clean dir at the start of a recheck so you are certain you are parsing the shipped bytes, not a stale working copy.
